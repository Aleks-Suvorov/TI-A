# TI-A on TradingView

Two scripts:

| File | Purpose |
|---|---|
| `TIA.pine` | the indicator — arrows, stop/target lines, explanation card, alerts |
| `TIA_strategy.pine` | the same model wired to TradingView's backtester |
| `frozen_model.json` | the trained constants both consume, generated by Python |

## Install

1. Open the Pine Editor, paste `TIA.pine`, save, "Add to chart".
2. **Wait ~350 bars.** The rank window is 252 bars and the higher-timeframe view
   needs more. Before that the script shows `WARMING UP` and emits nothing.
3. Set alerts on `TI-A BUY` / `SHORT` / `SELL` / `COVER` if you want them.

There are no model settings. That is deliberate — the design requirement is that
the trader configures nothing that affects a signal. The inputs that exist are
cosmetic, plus one risk percentage used only by the strategy version.

## What you will see

Mostly nothing. On synthetic data roughly 1% of bars are even structurally
eligible before the expectancy gate applies. A system that stands aside for weeks
is behaving correctly; see `docs/01-THEORY.md` §12 for why extreme selectivity is
the only defensible policy when the information coefficient is around 0.04.

The card always says why it stood aside.

## The five outputs

```
FLAT  --BUY-->   LONG      LONG  --SELL-->  FLAT
FLAT  --SHORT--> SHORT     SHORT --COVER--> FLAT
```

`SELL` closes a long and never opens a short. `LONG → SHORT` in one bar is
forbidden; a reversal costs two bars.

## Regenerating the frozen model

```bash
cd python
PYTHONPATH=src python3 -m tia.export
PYTHONPATH=src python3 -c "from tia.export import emit_pine_constants; \
  emit_pine_constants('../pine/frozen_model.json','../pine/TIA.pine','../pine/TIA_strategy.pine')"
```

Only the region between the `BEGIN/END FROZEN MODEL` markers is rewritten.
`FM_HASH` carries the config manifest hash — if it disagrees with
`Config.manifest_hash()`, the script and the research results describe different
systems.

## Honest limitations

**The most common repainting bug in published Pine** is
`request.security(..., expr)` without `lookahead=barmerge.lookahead_off`, which
serves the completed higher-timeframe bar to historical bars that could not have
seen it. Using `lookahead_off` *without* an `[1]` offset is also wrong, because
the in-progress higher-timeframe bar keeps updating intrabar. This script uses
both. If you modify it, keep both.

Beyond that:

* **Pine cannot learn.** The Edge Book and the calibration map are frozen at
  export time. A live Python system keeps updating them; this does not.
* **Pine sees one chart.** The system's statistical power comes from pooling the
  Edge Book across a universe. A single-symbol TradingView backtest is
  *statistically uninformative* about whether the edge is real — it can falsify,
  never confirm.
* **The variance-ratio statistic is approximated.** The port uses the
  homoskedastic form with a frozen null scale rather than the
  heteroskedasticity-robust one, which over-reads trend persistence during
  volatility clusters. This is the largest fidelity gap; see
  `docs/11-PINE-PLAN.md` §3.
* **Intraday participation carries a session cycle** the Python reference removes
  by normalising within time-of-day buckets. Prefer daily bars, or expect sweep
  detection to fire more readily near the open and close.
* **The current `frozen_model.json` was trained on synthetic data.** It is a
  smoke test. Do not trade it.

## Verifying the port against Python

`docs/11-PINE-PLAN.md` §7 gives the protocol and per-quantity tolerances. The
acceptance criterion: at least 90% of Python's actionable signals appear in Pine
within ±1 bar, and Pine emits no more than 1.25× Python's count. A port emitting
*more* signals than the reference has lost a gate.
